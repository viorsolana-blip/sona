# Sona security review — 18 October 2026

**Internal, AI-assisted review. This is not an independent security audit, certification, or guarantee.** The review covers the public Raydium CPMM Fee Key marketplace and its local reference implementation. No mainnet transaction was signed or submitted during the review. Test transactions used purpose-created assets and valueless SOL on an isolated validator.

Review baseline: `bb7f1e9692bca6ec9e11880f800f6589c1d33f81`. The accompanying machine-readable report binds the reviewed and patched files by SHA-256. The deployed build manifest identifies the release commit; recorded reports retain their own execution dates and scopes.

## Findings and changes

| ID | Severity and prerequisite | Finding | Resolution |
| --- | --- | --- | --- |
| SONA-01 | Medium; buyer previously approved a delegate for this mint's token account | An empty buyer ATA can retain a delegate that can transfer the NFT after receipt. Reproduced with real SPL instructions on a local validator. | Preparation and submission reject delegated or unsafe destination accounts. Owner, mint, program, layout, initialized/frozen state and close authority are checked. New unit and actual-validator regressions cover the behavior. |
| SONA-02 | Medium; authenticated unfunded or overcommitted wallets | Unsigned purchase requests could occupy per-listing/global capacity until the listing's long expiry. | Require balance covering asking prices across pending requests, cap each buyer at five requests, expire unsigned requests after 15 minutes and exclude expired requests from admission counts. Signed approvals remain protected until their chain validity is resolved. |
| SONA-03 | Medium; legitimate Fee Key holder repeatedly lists and cancels | Retired unsigned listing records could exhaust bounded D1 storage. | Bound recent retired listing history. Preserve listings referenced by trades, released signatures and finalized receipts. Repeated relist/cancel and retained-proof tests exercise the boundary. |
| SONA-04 | Medium; local reference server restarted with a different origin and the same database | The Node authentication path could accept a previously issued origin-bound challenge without rechecking the current origin. It also accepted the exact expiration boundary. The hosted path already checked origin binding. | Recheck origin/network challenge binding and reject at expiry. Tests reproduce origin changes and exact time boundaries. |
| SONA-05 | Defense in depth; malicious API or wallet-provider response | The client forwarded authentication text without independently validating its intended origin, account, purpose, network and lifetime. ## Verification method

The review used separate passes over chain validation, server authorization/state coordination and wallet/browser behavior. Findings were evaluated against code and adversarial tests; the delegated-token-account issue was reproduced on an actual local Solana validator. The shared chain validation checks canonical Raydium program-derived accounts, and both signing sides bind the same exact three-instruction transaction. Existing tests cover wrong signers, modified amounts/recipients, replay, rollback, competing buyers, interrupted submission and persistence.

The release verification record supplies exact commands, results and source hashes. Local validator results are not a mainnet sale, and a read-only mainnet observation is not ownership of that asset. Automated checks of wallet adapters are not a completed browser-extension signing session.

The final offline suite passed **148 tests**, with **2 optional validator cases skipped in that suite and executed separately**. Actual validator runs passed 14 Node backend checks, 10 hosted-adapter checks and both 6-case settlement suites. The security reproduction ran two additional cases against real SPL instructions.

## Remaining limitations

- **Not independently audited.** No external security firm or unrelated reviewer has attested this implementation. The separate passes were performed by AI agents within the same development session.
- **Build-time advisory:** `braces` 3.0.3 has GHSA-vfj7-8cjw-p6xm (stack exhaustion with deeply nested patterns), inherited through the Vinext build tooling. The six affected dependency nodes refer to this one advisory. The reviewed marketplace does not pass request input into those build-time glob functions. There was no patched `braces` release available from npm when checked. Build untrusted repositories only in an isolated environment; this is not a zero-advisory dependency graph.
- **RPC and external program trust:** finality and account reads rely on the configured public RPC and Solana. Raydium's deployed programs are external dependencies and were not audited here. Public RPC can throttle or fail.
- **Off-chain checks have timing limits:** the destination safety check does not revoke authorities and cannot stop a buyer changing account permissions afterward. Released seller signatures remain usable until their blockhash expires; a website cancellation alone cannot revoke them.
- **Abuse mitigation is bounded:** funding checks do not escrow or reserve funds. A funded distributed attacker can still consume free hosting/RPC capacity. No claim of Sybil-proof admission, unlimited availability or paid DDoS protection is made.
- **Hosted coordination:** D1 coordinates listings and purchases. Atomic SPL Token/SOL settlement is non-custodial, but the order service is centralized and can become unavailable.
- **A real mainnet sale remains separate evidence.** It requires a genuine supported Fee Key, consenting seller and buyer, their own signatures and network fees. A controlled transfer must not be described as independent customer adoption or trading volume.

## Reproduce

From the repository root:

```sh
npm ci
npm --prefix marketplace ci
npm --prefix marketplace run build
npm test
npm audit --omit=dev
npm audit
npm --prefix marketplace audit
```

With the documented Solana test validator installed, run the local integration and security reproduction commands listed in the machine-readable report. These commands use fresh test keys and isolated ledgers; they must never load a mainnet key. The read-only mainnet verification guide describes the separate public evidence workflow.
